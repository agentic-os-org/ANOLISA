# ANOLISA 文档规范：中文评审参考

[English](documentation-standard.md)

> 本文仅供中文阅读和评审参考，不是完整译文。实际规则以英文原文为准。

## 按读者的任务划分文档

先判断读者要完成什么，再决定把内容放在哪里。同一个命令可以服务不同任务。

| 读者要做的事 | 文档位置 | 内容范围 |
|---|---|---|
| 在自己的环境中安装、使用或维护 ANOLISA | `docs/user-guide/{en,zh}/` | 受支持的安装、配置、首次使用、升级、排障和恢复 |
| 在外部项目中接入或扩展 ANOLISA | `docs/developer-guide/{en,zh}/` | 公开 SDK、API、协议、Provider、适配器和集成验收 |
| 修改、验证或发布 ANOLISA 本身 | `CONTRIBUTING*.md`、`contribute/{en,zh}/` | 开发环境、构建与调试、回归与 PR 门禁、项目打包和发布 |
| 理解或改变组件内部实现 | 组件自身的 `docs/design/` 等内部文档 | 实现取舍、私有接口、不变量、实现或迁移计划 |

安装后确认功能是否生效是用户任务；验证外部系统是否正确接入是开发者任务；验证
源码改动是贡献者任务。现有共享 `getting-started/building.md` 和 `testing.md`
暂时保留在原路径，后续再按任务拆分。组件设计的放置规则不改变全局或跨组件 ADR
的归属、位置和评审流程。评审状态与实现、验证和发布状态分别记录。

## 从源码安装如何组织

优先提供目标平台和版本可取得、受支持的安装方式。适用时优先给出 `anolisa install`
入口；RPM、独立安装包等渠道按实际支持情况说明。写清安装范围和权限。如果只提供
Preview，说明版本或提交、制品来源和限制。

如果项目支持用户构建并使用源码产物，用户指南可以列为安装备选：说明何时选择它、
支持的平台和 release tag 或明确的 Preview 提交，以及构建完成后如何安装和验证。
**工具链、构建命令和产物路径只在贡献指南的独立构建章节维护。** 用户可以直接阅读
那一节，无需配置贡献者工作流或运行 PR 门禁。仅用于源码调试或验证改动的构建路径，
不列为用户安装方式。

## 编写与评审时检查什么

- 修改文档或公开行为前，先读英文规范，再按内容涉及的组件查阅其 `AGENTS.md`，
  即使待改页面位于 `docs/` 或 `contribute/`。
- 动笔前确定读者、任务、适用版本和权威页面。核对目标版本的实现、CLI 和 schema；
  安装与支持承诺还要核对实际发布或 Preview 制品及验证范围。
- 操作步骤给出相关前置条件、工作目录、权限、可观察结果，以及必要的停止或回退方式。
  构建成功、服务已启动和能力已生效，需要不同证据。
- 同一公开契约或流程维护一份权威说明。其他入口可用摘要、链接或生成内容；
  不把未实现功能、开发专用步骤或未验证的环境组合写成受支持的使用路径。
- 同一 PR 更新受影响的权威页面与双语对应章节。公开 SDK、API 或 Provider 协议变更
  要同步开发者参考；如果用户操作或支持范围也变了，再同步用户指南。
- 迁移文档时维护公开 URL 和锚点，并同步受影响的导航和生成入口。在 PR 中说明
  哪些内容经过源码核对、样例解析或实机运行，并如实列出尚未验证的范围。
