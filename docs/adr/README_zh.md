# 架构决策记录

[English](README.md)

本目录集中存放 ANOLISA 的所有架构决策记录（ADR），包括系统级、跨组件及单组件
决策。所有记录共用一个编号序列，并在各自的元数据中注明范围。

每份 ADR 的架构决策以英文原文为准。所有其他语言译文仅供参考；如有差异，以英文
原文为准。

## 评审流程

1. 遵循[贡献指南](../../CONTRIBUTING_zh.md)，提交聚焦单一决策的 PR，ADR 状态先保持
   `Proposed`。
2. 手动请求受影响组件的负责人评审。中央 ADR 路径不会通过 `CODEOWNERS` 自动请求
   这些组件负责人。
3. 解决评审意见并就决策达成共识，更新下方的采纳元数据，取得对最终版本的批准，
   再由维护者合入官方 `main`。此次合并标志着已采纳决策正式生效。

采纳时，更新正文元数据：

```markdown
- **状态：** Accepted（已采纳）
- **日期：** YYYY-MM-DD
- **决策日期：** YYYY-MM-DD
- **决策 PR：** <PR URL>
```

原有日期保留为提案日期；决策日期填写采纳日期，决策 PR 链接到评审。采纳不改变
实现基线。讨论与批准记录保留在 PR 中。

同步英文正文、各语言译文、两份索引及资源中显示的 ADR 状态。`Accepted` 表示架构
已采纳，实现仍可能尚未完成。图中的提议集成标签和虚线不会仅因 ADR 被采纳而改变。

## 生命周期

| 状态 | 含义 |
| --- | --- |
| Proposed | 讨论中，尚未形成已采纳决策。 |
| Accepted | 已通过评审，并合入官方 `main`。 |
| Rejected | 已评审并明确不采用。 |
| Superseded | 已被后续通过的 ADR 替代。 |

改变已采纳的架构决策时，应新建 ADR。替代决策被采纳后，将旧记录标为 `Superseded`，
在两份记录之间添加双向链接，并保留原有理由。文字勘误、链接修复及翻译修正可以
通过 PR 直接更新原记录。
