tokenless 用来压缩 Agent 发给模型的上下文。但只报一个压缩率说明不了问题：某个压缩器可能在一份载荷上表现很好，代价却是丢掉了 Agent 三轮之后才用到的关键信息。所以这套评测分了四层，每层负责上一层看不到的部分。

所有压缩率都用 tiktoken 对实际输出重新计数，不采用引擎自报的数字，这样每个数都能追溯到压缩器本身。

## 四层结构

| 层 | 测量范围 | 要回答的问题 | 状态 |
|---|---|---|---|
| **L1** 组件层 | 单个压缩器，单份标准输入 | 每个压缩器功能是否正确，开销多大？ | 已有结果 |
| **L2** 模块层 | 一轮工具输出，五类载荷 | 在真实载荷上省了多少、丢了什么？ | 已有结果 |
| **L3** 场景层 | 整段对话，多种场景形态 | 信息能否在整个消息列表里留存，而不只是单条响应？ | 已有结果 |
| **L4** 端到端层 | 完整的 Agent 任务 | 任务还能不能做成，总体代价多少？ | 结果见下 |

每层单独维护自己的 harness 和报告。不同层的数字不混用，因为它们测的不是一回事。

---

## L1 组件层

**测什么。** 把每个压缩器单独拿出来，在它对应输入类型的标准 fixture 上测。看三件事：功能是否符合规格、单次调用的开销、开销随输入增大如何变化。用例里包含对抗样本和 round-trip 校验，避免压缩器靠悄悄降级输出蒙混过关。

**不测什么。** 这份节省值不值得。这里的压缩率只是某份 fixture 上的结果，不能当作生产流量上的预期值。

### 结果

`o200k_base` 计数，Linux x86_64。

| 压缩器 | 输入 | 钩子 | 压缩率 | 耗时 |
|---|---|---|---|---|
| **ResponseCompressor** | JSON / API / 工具响应 | PostToolUse | **65.8%** | 46.93 µs |
| **SchemaCompressor** | OpenAI function-calling 工具 schema | BeforeModel | **47.3%** | 11.40 µs |
| **TOON encoder** | JSON 转紧凑 TOON | 接在 ResponseCompressor 之后 | 17.0%（response）/ **−2.3%**（schema） | 3.92 – 10.46 µs |
| **RTK rewriter** | shell 命令输出 | PreToolUse · Shell | 58.6 – 98.6% | 主要开销在进程启动 |

<Callout type="warning" title="TOON 处理 schema 时会变大">
TOON 压 response 载荷能省 17.0%，但压工具 schema 反而多出 2.3%。它本质是一种表格编码，同构数组上收益明显，而 function-calling schema 嵌套深、字段异构，用它就是净亏。建议按载荷类型分别开启，不要全局打开。
</Callout>

### 数组截断的成本上限

ResponseCompressor 默认在第 32 项截断数组。超过这个阈值后，压缩器不再往下遍历，但整体耗时仍随输入增大而上升：

| 数组规模 | 耗时 |
|---|---|
| 10 项 | 11.51 µs |
| 31 项 | 36.84 µs |
| **32 项（阈值）** | **38.18 µs** |
| 33 项 | 38.39 µs |
| 100 项 | 54.11 µs |
| 1,000 项 | 275.04 µs |

耗时随载荷体量基本呈线性：1 KB 5.50 µs，10 KB 38.62 µs，100 KB 104.80 µs，1 MB 815.01 µs。

<Callout type="info" title="大数组上的高压缩率来自截断">
超过 32 项之后，省下来的是被丢掉的尾部，不是把整个数组编得更紧凑。这也是 L2 存在的原因：不知道尾部原本装了什么，截断算出的压缩率就说明不了问题。
</Callout>

### 测试覆盖

96 项测试通过，其中 9 项 RTK 协议测试针对固定版本的真实 `rtk` 二进制执行，没有跳过。

| 压缩器 | 测试数 |
|---|---|
| ResponseCompressor | 34（保留、健壮性、最坏情况、回归守卫） |
| SchemaCompressor | 25 |
| TOON encoder | 18（round-trip 与对抗样本） |
| RTK rewriter | 9（真实执行） |

这里的覆盖指枚举出的合法取值和规则都跑过了，不代表在任意输入或生产任务上同样准确。

## L2 模块层

**测什么。** 一轮工具输出，覆盖 Agent 实际会碰到的五类载荷：`json`、`command`、`grep`、`code`、`diff`。重点从"功能对不对"转向"省下来的代价是什么"，因此每类都同时看压缩率、两种独立的语义保留度量，以及标明基准的耗时。

**不测什么。** 跨轮次的情况。某个信息在这条响应里还在、但五轮之后才被用到，这属于 L3。

### 压缩率与语义保留

`N` 指独立观测数，以实际测到的载荷为键：如果一条命令多轮输出字节完全相同，不论跑几轮都只算一次。

| 类别 | 压缩率 ± 95% CI | N | 压缩前（token） | 保留率 | 语义完整度 |
|---|---|---|---|---|---|
| **diff** | **76.0%** [37.8, 97.6] | 5 | 37,775 | 15/25 | **0.64** ⚠ |
| **json** | **44.6%** [18.0, 62.2] | 3 | 1,603 | 8/11 | **0.80** ⚠ |
| grep | 0.0% [0.0, 0.0] | 8 | 776 | 40/40 | 1.00 |
| command | 0.0% [0.0, 0.0] | 2 | 1,429 | 6/6 | 1.00 |
| code | 0.0% [0.0, 0.0] | 9 | 509 | 37/37 | 1.00 |

<Callout type="info" title="压缩率为 0 的行不说明质量">
`command`、`code`、`grep` 压缩率是 0%，输出和输入一样，保留率满分是必然结果。这些 `1.00` 的意思是"什么都没改"，不是"什么都没丢"。
</Callout>

### 两种语义度量

单看任何一种都容易得出错误结论，所以两种都做：

| 度量 | 检查什么 | 怎么判 |
|---|---|---|
| **保留率** | 原文的关键信息压缩后是否逐字还在 | 确定性的字符串或正则匹配 |
| **语义完整度（S）** | 原文能答对的问题，压缩后还能答对多少 | 逐题判定，在压缩输出上评分 |

S 按题计分，丢掉一个信息不能靠蒙对另一题补回来。低于 0.85 会告警。

**能压缩的两类，正好也是丢信息的两类。** diff 和 json 是唯一真正发生压缩的两类，也恰好是唯一跌破门禁的两类。这不是抽样波动，而是策略本身导致的：数组截断丢的是尾部条目，而被引用的关键信息有时正好在那里。

<Callout type="warning" title="输出合法不等于内容完整">
压缩后的输出格式依然规整。在激进读取模式下，约 9 KB 的代码 diff 被压到 167 字节，仍是合法文本，但改动涉及的函数名和常量已经全部不在了。使用方从输出本身看不出少了东西，这比直接报错更麻烦。
</Callout>

### 压缩率取决于调用入口

RTK 按子命令选择过滤策略，同一份内容换个调用方式，结果差别很大。下面在一份固定入库的约 9,200 字节代码 diff 上实测，这份 diff 含 5 个代码标识符：

| 调用入口 | 输出 | 压缩率 | 标识符保留 |
|---|---|---|---|
| 全文读取 | 9,211 B | 0.0% | 5/5 |
| 结构化 diff 过滤 | 约 8 KB | 91% | 5/5 |
| 激进过滤 | 167 B | **98.2%** | **0/5** |
| 两行摘要 | 47 B | **99.5%** | **0/5** |

判断某条具体调用路径时，要看对应入口的数据，不要用聚合值。"diff 能压 90% 以上"这句话必须说明是哪个入口才成立。

### 耗时

| 类别 | p50 | p95 | p99 | 计时基准 |
|---|---|---|---|---|
| code | 0.006 ms | 0.006 ms | 0.008 ms | 进程内 |
| json | 0.007 ms | 0.039 ms | 0.049 ms | 进程内 |
| command | 5.668 ms | 6.114 ms | 6.125 ms | 包裹减裸跑 |
| grep | 6.089 ms | 6.925 ms | 6.994 ms | 包裹减裸跑 |
| diff | 9.400 ms | 19.346 ms | 20.239 ms | 包裹减裸跑 |

进程内压缩是微秒级。`command`、`grep`、`diff` 上的毫秒级数字主要来自 RTK 的进程启动，不是压缩本身：同一个引擎在进程内调用时 p99 不到 0.05 ms。`diff` 的 p99 和 p50 很接近，说明这是稳定的固定开销，不是长尾问题。

<Callout type="info" title="不同计时基准之间不能横向比较">
进程内计时只框住 compress 调用。"包裹减裸跑"指整个包裹进程的墙钟时间减去裸命令的耗时。只在同一基准内部比较才有意义。
</Callout>

### 全任务汇总

三个多步 Agent 任务，按每次交互累计，不按单条响应。这是 L2 能做到的最接近任务视角的形式，真正的任务视角要等 L4。

| 任务 | 交互轮次 | 压缩前 | 压缩后 | 节省 | 节省率 |
|---|---|---|---|---|---|
| review | 3 | 91,478 | 9,046 | 82,432 | **90.1%** |
| bug-hunt | 4 | 94,008 | 11,576 | 82,432 | **87.7%** |
| api-debug | 4 | 9,354 | 3,600 | 5,754 | **61.5%** |

两个大任务主要由 diff 载荷贡献，8 万多 token 的节省来自那里，所以前面记录的语义代价同样适用于这两个任务。`api-debug` 以 JSON 为主、体量小一个数量级，节省率偏低就是因为没有超大数组可截。

## L3 场景层

**测什么。** 整段对话，也就是 Agent 实际发给模型的那份消息列表，而不是单条响应。37 个场景（场景套件 34 个 + 流水线套件 3 个），覆盖 8 类内容形态，每类再分几个体量档位，压缩前合计约 344 万 token。

**为什么需要这一层。** L2 只测一轮。但 Agent 的上下文是跨轮次累积出来的消息列表，单条响应的压缩率看不出这份列表整体的变化：某个信息可能在它出现的那条响应里还在，等模型真要用的时候已经没了。

**不测什么。** 反馈回路。一条被压缩的工具结果会改变 Agent 下一步的动作，下一步又改变下一份载荷，这属于 L4。

37 个场景中有 24 个进入压缩通道，其余场景的载荷形态不在当前适用范围内（见下文「适用范围」）。

### 压缩率与关键项保留

只统计 24 个进入压缩通道的场景。`N` 是该类里有入口的场景数，区间由 bootstrap 在场景之间聚合而得。"关键项"是每个场景预先标注的必须保留的事实——记录总数、错误项、边界数值等——按确定性匹配检查压缩后是否还在。

| 内容类型 | N | 压缩率 ± 95% CI | 单场景范围 | 关键项保留 |
|---|---|---|---|---|
| **logs** | 4 | **91.2%** [79.6, 98.3] | 73.8 – 99.4% | **13/20 = 65.0%** ⚠ |
| **json** | 14 | **82.7%** [68.5, 92.8] | 1.5 – 99.4% | **18/35 = 51.4%** ⚠ |
| agentic | 5 | 41.7% [30.5, 47.6] | 19.4 – 48.0% | 667/694 = 96.1% |
| schema | 1 | 36.9%（退化为点） | — | 41/41 = 100% |

按内容类型等权，关键项保留是 **78%**。

<Callout type="warning" title="不要用池化总数">
把四类的关键项直接加总会得到 739/790 = 94%，但 agentic 一类就占了这个分母的 88%（694 项），而它恰好保留得最好（96.1%）。丢得最狠的 json（51.4%）和 logs（65.0%）合起来只占 6.9%，被稀释到看不见。本页一律按内容类型分别呈现，等权平均 78%，不采用那个 94%。
</Callout>

### 适用范围

tokenless 的压缩器接受结构化载荷：JSON 工具响应走 `compress-response`，工具 schema 走 `compress-schema`。本层同时记录这一适用边界，而且是否适用由实测载荷决定，不看消息角色：

| 内容类型 | 场景数 | 进入压缩通道 | 说明 |
|---|---|---|---|
| json | 14 | 14 | 结构化 JSON 工具响应 |
| agentic（多轮工具轨迹） | 5 | 5 | 消息列表里的 JSON 工具消息 |
| logs | 4 | 4 | 结构化日志数组 |
| schema（工具 schema） | 1 | 1 | function-calling schema |
| code | 4 | 0 | 载荷为裸代码，不在结构化输入范围内 |
| text（散文文档） | 4 | 0 | 载荷为裸文本，同上 |
| rag（检索上下文） | 4 | 0 | 载荷在 system / user 散文里，既无 tool 消息也无 tools 数组 |
| simple | 1 | 0 | 同上 |

这四类要进入压缩通道，需要一条非 JSON 载荷的处理路径。

<Callout type="info" title="这四类不计入压缩率统计">
它们记录的是"不在适用范围内"，不是"压了但没省"，所以不当作 0% 压缩率计入上表；反过来，它们未压缩原文的关键项保留必然满分，那个满分同样不计入保留率。
</Callout>

### 压缩的语义代价

和 L2 一样用两种度量：确定性的关键项匹配，以及语义探针。探针共问 48 题，其中原文能答对 31 题，压缩后仍能答对 **23 题（74%）**。

丢失高度集中在两类信息：

- **记录总数。** `api_responses_500`、`database_rows_1k`、`search_results_500` / `_1000`、`structured_100` 压缩后答不出"一共多少条记录"。
- **错误项。** `search_results_100` / `_500` / `_1000` 压缩后无法引用工具输出里报告的错误消息；关键项层面共有 15 个场景至少丢掉一条 `error_entry`。

另有 2 个场景（`number_array_200`、`number_array_1000`）丢掉了数组里的极值项。

根因和 L2 同源：数组截断丢的是尾部条目，而总数、错误项和极值经常正好在尾部。在整段对话里这类信息往往是 Agent 后续决策的依据，丢失比单轮更实在。

体量越大，这个代价越明显。同一种载荷形态（结构化日志）的四个档位：

| 场景 | 压缩前（token） | 压缩率 | 关键项保留 |
|---|---|---|---|
| structured_100 | 8,612 | 73.8% | 5/5 |
| structured_500 | 40,491 | 94.5% | 3/5 |
| structured_1000 | 80,291 | 97.2% | 4/5 |
| structured_5000 | 398,120 | **99.4%** | **1/5** |

趋势不是严格单调——1K 档比 500 档多留了一项，因为具体哪几条错误落在被截掉的尾部有偶然性——但方向清楚：压缩率靠丢弃尾部往上走，尾部装着的关键项就跟着掉。

### 耗时

进程内计时，只框住压缩调用本身，不含进程启动或序列化。下表取 24 个真正发生压缩的场景：

| 统计量 | 值 |
|---|---|
| p50 | 0.18 ms |
| p95 | 4.69 ms |
| p99 | **13.28 ms** |

p99 来自最大的那个场景（`multi_tool_100t`，压缩前 61.5 万 token）。

<Callout type="info" title="报告文件里的 p50 更低，因为它把没压的场景也算进去了">
`report.json` 的汇总覆盖全部 37 个场景，其中 13 个没有压缩入口、记为 0 ms，所以那里的 p50 是 0.032 ms。上表只取实际压缩过的 24 个，是更能反映压缩开销的口径。24 个观测下 p99 就等于最大值，粒度很粗。
</Callout>

### 门禁与信号

**门禁。** 场景探针成功率下降不得超过 5%。本轮共 23 条信号：

| 类型 | 数量 | 含义 |
|---|---|---|
| retention | 13 | 关键项保留低于阈值，全部落在 json（10）与 logs（3） |
| probe_drop | 6 | 探针成功率下降超过 5% |
| capability_gap | 4 | 该内容类型不在当前适用范围内 |

### 几个影响结果解读的设计选择

- **场景资产一次生成后固化入库**，不在运行时构建。上游生成器用 `uuid4` 生成 tool-call id，固定随机种子约束不住它，如果每次运行现生成，载荷都会变，跨运行之间就没法比。
- **是否适用由实测载荷决定，不看消息角色。** 一条装着裸文本的 tool 消息不会进入压缩通道，如果把它记成 0% 压缩率，就把适用边界说成了压缩失败。这类场景单独记在「适用范围」里，不计入压缩率与保留率。
- **不确定性在场景之间聚合，不在重复轮次之间聚合。** 资产是静态的，压缩器是确定性的，单个场景的区间必然退化成一个点，靠加重复轮次去压窄它属于伪重复。
- **语义探针以 contains-answer 为主判据，同时给出 token 级 F1**，并且只统计原文能答对的问题，模型本来就答不出的不算在压缩器头上。回答问题的是一个固定模型，但**判分不用 LLM 当裁判**：门禁看的是压缩前后的差值，而裁判本身的波动会放大或掩盖这个差值，且分不清是哪种情况。

## L4 端到端层

**测什么。** 一个完整的 Agent 任务，从第一条提示到最终补丁，全程开着压缩——关注使用者最终真正在意的两件事：任务还能不能做成，一共花了多少。48 个 SWE-bench Lite 修 bug 实例，按每台主机 12 个分片到 4 台主机，使每台都跑全部分组，在 temperature 0 下重复五轮。

每实例对比四个分组：**A** 不压缩（基线）、**B** tokenless、**C** 参照压缩器（默认）、**D** 参照压缩器（tool-results 模式）。

**为什么需要这一层。** L1 到 L3 测的都是压缩器面对固定载荷或固定对话时的表现，都观察不到反馈回路：一条被压缩的工具结果会改变 Agent 下一步的动作，下一步又改变下一份载荷。这种累积效应只有跑完整任务才看得见——而它恰恰是「单请求节省」与「端到端节省」的分野。

### 单请求的节省不会变成端到端的节省

在它触达的请求上，参照压缩器省下约 10% 的线级输入 token（C 10.03%、D 10.12%；在 66–69% 的请求上生效），与 L1–L3 的单载荷数字一致。tokenless 的压缩钩子在全部 48 个实例上都触发了，但 harness 在该侧未采集线级计数，因此对它只证明了「已激活」。

然而这些都没有复合成整任务的 token 下降。按实例配对（难度抵消）并重复五轮，**每个分组的 prompt token 比值在每一轮都跨在 1.0 两侧：**

| 分组 vs 基线 | prompt token 比值，五轮 | 端到端判定 |
|---|---|---|
| **B** tokenless | 1.10 / 1.01 / 0.94 / 1.00 / 0.97 | 无可复现效应 |
| **C** 参照（默认） | 0.92 / 0.99 / 0.98 / 1.09 / 0.91 | 无可复现效应 |
| **D** 参照（tool-results） | 1.12 / 1.10 / 1.08 / 1.15 / 1.04 | 小幅、持续**增加** |

整个矩阵里只有一个 95% CI 排除了 1.0——tokenless 在第一轮的*请求数*——且后四轮未再复现。分组 D 是唯一的单调规律：其 tool-results 模式在每一轮都高于 1.0，即在本负载上它增加了 prompt token 而非减少。端到端结果是个零结果：单请求测到的节省没能挺过 Agent 轨迹的漂移。

### 解决率

每个产出补丁都经 SWE-bench 测试 harness 评分（`FAIL_TO_PASS` 须由失败转通过、`PASS_TO_PASS` 须保持通过）。池化解决率为 **73–76%，且四个分组之间在统计上无法区分**——压缩对「能否修好 bug」既不帮忙也不拖后腿。

该解决率之所以高，是因为语料是 guided 的（见告示框），所以它是语料的属性、不是能力分，且不可与公开 SWE-bench 成绩比较。真正有信息的是失败尾部：一小组实例在每一轮、每一分组都失败，而它们恰恰是「prompt 点名了待改文件、却一行修法都没泄露」的那些。在这些实例上，Agent 改对了文件，却产出无法让目标测试通过的改动——只把位置交给它还不够。

<Callout type="warning" title="语料是 guided 的，这把双刃剑砍两边">
这些 prompt 不是盲写的 bug 报告：已记录 campaign 的旧版审计按「完整路径或 basename 命中」口径测得 80% 恰好匹配一个 gold 源文件名，约五分之一复制了 ≥75% 的 gold 补丁自身新增行。常见 basename 会抬高该 80%；当前审计已分别报告严格完整路径命中与仅 basename 命中，因此在重新运行语料审计前不推断严格路径口径的比例。这种引导仍会**抑制被测的效应**（prompt 本就很小、且部分已被预解，压缩器无从压缩），并**抬高解决率**（模型常被直接递上答案）。零 token 结果与 73–76% 的解决率都须在此背景下解读；两者都不可外推到开放式 Agent 工作。
</Callout>

### 可复现性底线

temperature 0 下运行并不可复现：五轮之间**无一实例复现了自己的 prompt token 总数**，每实例变异系数中位为 21–27%。上面的分组间差异（5–12%）小于这一噪声底线，因此该零结果应读作「在轮间噪声之上检不出效应」，而非「实测为零」。仅靠扩大实例集无法解决；须先把每个实例在各轮上取平均再配对。

---

## 方法

1. **只用一个权威计数器。** 所有表头压缩率都用 tiktoken（`o200k_base`）对实际输出重新算。组件自己报的数字不作为表头结论。
2. **独立性以载荷为键。** 确定性命令重复执行只算一次观测。已实测：`git log`、`git show`、`git diff` 各跑 5 轮都只产生 1 份唯一输出，`rg` 产生 5 份。
3. **区间用 bootstrap 算**（10,000 次重采样，固定 seed），只在独立观测上做。完全确定性的类别区间会退化成一个点，这一点如实标出，不做掩盖。
4. **没发生压缩的地方不算保留率贡献**，因为未改动载荷上的满分不构成证据。
5. **测内容，不测格式。** diff 的真值取自变更行（`+`/`-`）里的标识符，这样只保留 diff 框架、把正文丢掉的压缩器不会被判成无损。
6. **自洽性校验。** 未压缩的原文必须能通过针对它本身的那些检查项，通不过就判定为 harness 缺陷，绝不记成产品缺陷。
7. **每个指标配一个反向对照。** 必须证明一份本该失败的载荷确实会失败，否则指标可能因为什么都没测到而通过。

## 局限

引用上面任何数字之前，请先了解这些边界：

- **样本多样性是 L2 目前最主要的约束。** json 有 3 个独立样本，diff 有 5 个入口，command 只有 2 个。`command` 和 `code` 的区间退化成了一个点（`[0.0, 0.0]`），因为每次观测完全一样，点估计可信，但区间不携带任何不确定性信息，结论不能外推到别的输出形态。
- **diff 的表头数字是多入口聚合，不是单一压缩率。** 76.0% 的区间宽到 `[37.8, 97.6]`，正是因为同一份内容在不同入口下从 0% 到 99.5% 都有。
- **json 的均值掩盖了很大的样本间差异**：三份同类型载荷分别是 18.0%、53.5%、62.2%。制约因素是样本多样性，不是重复次数。
- **RTK 输出过滤是手工采集的**，只实测过一次，没走自动化 harness。它作为实测观察值给出，不算可复现测试。
- **语义探针依赖单一模型。** 温度已固定以保证可复现，但绝对分数受该模型能力影响，压缩前后两种条件的对比比绝对值更可靠。
- **L1 的压缩率是逐 fixture 的**，每个数字都是该压缩器在自己标准输入上的结果，不代表任意生产载荷上的预期值。
- **非代码 diff 测得没那么准。** 内容抽取的兜底规则在文档、配置类 diff 上会退化成抽普通英文词，区分度不如代码 diff。
- **L3 的场景资产是合成生成的固定资产**，不是从生产流量里抓的。结论适用于这些形态和体量档位，往真实负载外推需谨慎。
- **L3 的探针基线题量很小。** 48 问里原文只能答对 31 问，单个场景只有 1–3 题，所以"下降 50%"这类数字来自很小的分母，宜看方向不宜看精度。
- **L3 关键项的分母分布极不均衡。** agentic 一类就占 88%，所以任何跨类型池化的保留率都会被它主导；本页因此只给分类型数字和等权平均。schema、simple 两类只有 1 个场景，区间退化成一个点。
- **L3 的 37 个场景里有 2 对近重复。** 流水线套件的 `agentic` 与场景套件的 `multi_tool_50t`、流水线套件的 `rag` 与 `document_qa_20000` 是同一配置下分开生成的，只差在 tool-call id 上，不是相互独立的观测。agentic 的 694 个关键项里有 139 个（约 20%）来自这对近重复。
- **L4 数字描述的是 guided 语料，不是开放式 Agent 工作。** prompt 泄露了待改文件、常常还泄露部分修法，这既抑制了任何压缩效应、又抬高了 73–76% 的解决率。不要把零 token 结果读作「压缩在端到端上普遍免费」，也不要把解决率当作 SWE-bench 能力分。
- **L4 在 temperature 0 下不可复现。** 五轮之间无一实例复现自己的 prompt token 总数（中位 CV 21–27%），因此分组间 token 差异位于噪声底线之下：请读作零结果，而非实测的零。
