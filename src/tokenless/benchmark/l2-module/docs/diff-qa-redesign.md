# L2 diff 压缩 QA 重设计方案

> 需求背景：**对压缩效果进行语义评价时，应该关注内容而非压缩之后的格式，
> 当前 QA 测试设计不太合理，需要重新设计。**

## 1. 现状与问题（已核实）

L2 对 diff 类压缩质量的评价有两条通道，**两条都在验证「长得像不像 diff」，
而非「diff 说了什么」**。

### 1.1 Rule-based（retention / ground_truth）

`src/l2/samples.rs::extract_dynamic_ground_truth`（L229）对 diff 类只用一条正则：

```
^diff --git a/(\S+)
```

即只抽取**被修改的文件路径**，retention 只检查「压缩后这些路径行是否还在」。

问题：一个压缩器只要保留每个 `diff --git a/xxx` 头、把实际增删代码全部删掉，
retention 依然满分。文件路径是 diff 的**格式框架**，不是它承载的内容。

### 1.2 LLM-based（语义探针 probe）

`assets/probes/git_diff.json` 现有 8 个问题，其中 7 个是纯格式问题：

| # | 问题 | 性质 |
|---|------|------|
| 1 | 是否用 unified diff 格式、有 `diff --git` 头 | 格式 |
| 2 | hunk 头是否以 `@@` 开头 | 格式 |
| 3 | 新增行是否有 `+` 前缀 | 格式 |
| 4 | 路径是否有 `a/` `b/` 前缀 | 格式 |
| 5 | 是否有携带 blob hash 的 `index` 行 | 格式 |
| 6 | 是否有文件路径在 src/tokenless 下 | 路径（半格式） |
| 7 | 是否由 git 产生 | 格式 |
| 8 | 说出一个 `diff --git` 头里的文件路径 | 路径 |

同样的毛病：把 diff 正文删光、只留框架，这 7 题照样全对。

### 1.3 后果

diff 类实测压缩 91.1%、retention 7/10、语义分 0.80——但这些数字衡量的是
「框架保留度」。真正该问的「哪个函数被改了、改成什么、错误处理有没有动」
根本没测。这正是需求指出的「关注格式而非内容」。

## 2. 重设计目标

QA 应回答**内容级问题**：压缩后，一个 agent 还能不能从 diff 里看出
**实质代码变更**——新增/删除了哪些函数、常量、关键行，改动落在哪个 hunk。

两条通道都要重做（本任务采用 rule-based + LLM-based 双轨）。

## 3. 方案 A：Rule-based 内容级 ground_truth

把 diff 正文按内容抽取关键事实，替换「只抽文件路径」。

### 3.1 抽取规则（对 `+`/`-` 变更行，而非头部）

从 diff 的**增删行**（以 `+`/`-` 开头、但排除 `+++`/`---` 文件头）中提取：

| 事实类型 | 正则/规则（示意） | 例 |
|---------|------------------|-----|
| 变更的函数/方法名 | 增删行里的 `fn \w+` / `def \w+` / `func \w+` | `fn compress` |
| 变更的常量/字段 | 增删行里的 `const \w+` / `pub \w+:` / `let \w+ =` | `MAX_DYNAMIC_ITEMS` |
| 变更的字符串字面量 | 增删行里的显著字符串（错误码、marker） | `<<tokenless:` |

> 本节是设计阶段的构想。最终实现的抽取顺序见 §8——其中「hunk 上下文定位」
> 一项**未实现**：`@@ ... @@` 头本身是格式而非内容，且 git 附在 hunk 头尾的函数
> 上下文并不总是存在，作为真值不可靠。实现改为只读增删行本身。

保留 rule-based 的价值：确定性、可复现、无需 API。

### 3.2 保留原有一条作为「格式基线」（可选）

可保留「文件路径」作为**一个**次要项，但权重下降；主体是内容级事实。
这样既能发现「整个文件的改动被丢」，也能发现「文件框架在但内容没了」。

### 3.3 体量与去重

沿用现有 `MAX_DYNAMIC_ITEMS` 上限；同一事实去重；
对动态类别同时记录「本次提取到的全集」（见依赖的 Bug：retention failures
未聚合问题——内容级 QA 更需要记录检了哪些项才可解释）。

## 4. 方案 B：LLM-based 内容级探针

重写 `assets/probes/git_diff.json`，把格式问题替换为内容问题。

### 4.1 新问题方向（内容级，answer 用内容而非 yes/no）

- 「diff 里新增或修改了哪个函数？给出函数名。」
  → expected_contains = 该 diff 实际改动的函数名
- 「被修改的常量/配置项的名字是什么？」
- 「这次改动删除了哪一行关键逻辑？引用其中的标识符。」
- 「改动主要落在哪个文件的哪个区域（函数/模块）？」

### 4.2 与动态数据的矛盾及解法

diff 是运行时生成的（`git diff HEAD~5 HEAD`），内容随 HEAD 变化，
所以**探针的 expected_contains 不能写死在 json 里**。两个可选实现：

1. **动态生成探针答案**：与 rule-based 共用抽取结果——先从当次 diff 抽出
   内容级事实（方案 A 的产物），再把这些事实作为探针问题的 ground truth，
   问模型「压缩后还能否答出这些事实」。这样两轨用同一套真值，一致且可解释。
2. **固定一个静态 diff 样本**：为 diff 类新增一个内容已知、不随 HEAD 变的
   committed 样本（像 json/code 那样），探针答案写死。牺牲「真实仓库 diff」
   的真实性，换来可复现与可写死答案。

推荐 **1**：保留 diff 的真实性，探针与 retention 共享动态抽取的内容事实，
既落实「关注内容」，又不引入不可复现的写死答案。

## 5. 影响评估

- **会改变 L2 报告数字**：diff 类的 retention 与语义分会重算，
  且大概率**下降**——因为现在测的是更难的内容级保留，而 tokenless 的
  截断策略正是丢内容的。这是预期的、正确的变化：让数字反映真实语义损失。
- 报告需重跑（远端），并在报告里说明 diff QA 口径已从「格式」改为「内容」，
  新旧数字不可直接比较。
- 与 tokenless 语义损失 bug（json/diff S=0.80）联动：重设计后 diff 的
  语义分可能更低，会强化那个 bug 的证据。

## 6. 交付清单

1. `src/l2/samples.rs`：`extract_dynamic_ground_truth` 的 diff 分支改为内容级抽取。
2. `assets/probes/git_diff.json`：**实际走了第三条路**——既未重写也未改模版，
   而是整个删除：diff 的探针问题由 `diff_probe_questions` 每轮从内容生成，
   静态资产无处可用。`probe_file_stem(Category::Diff)` 相应返回 `None`。
3. 探针与 retention 共享动态抽取结果的接线（方案 B-1）。
4. 单元测试：构造一个已知增删内容的 diff，断言抽取到函数名/常量而非仅路径。
5. 远端 fmt/clippy/test 全绿；重跑 L2 报告并更新口径说明。

## 7. 验收标准

- diff 类的 ground_truth / 探针问题以**内容级事实**为主（函数名、常量、
  关键逻辑行），文件路径至多作为次要项。
- 一个「只保留 diff 框架、删除正文」的构造输入，在新 QA 下 retention 与
  语义分显著低于满分（证明新 QA 真的在测内容）。
- 报告说明口径变更，新旧不可比。

## 8. 抽取优先级与残留局限

内容抽取按四级优先级取事实，每个变更行最多产出一条：

1. **定义名**——`fn`/`def`/`func`/`struct`/`enum`/`const`/`class` 等关键字后的标识符。
2. **引号内字符串**——错误码、消息、版本号通常在这里。
3. **路径式 token**——文件被移动或改名时，路径本身就是内容。
4. **兜底：最长的标识符式 token**，且过滤两类词——英文散文连接词，以及语言保留字。

第 4 级的过滤是必需的，不是优化。早期版本只取「最长 token」，在文档或配置 diff 上会抽到 `because`、`available` 这类词；而 `-    return;` 这类行会抽到 `return`。这两类词几乎在任何压缩输出里都存在，于是变更行被整行丢弃时 retention 仍然通过——属于假阴性。保留字过滤存在理论上的误伤：列表中多数是严格保留字，但 `print` / `range` / `module` / `function` / `type` 等在部分语言（如 Python）里是内建或上下文关键字，也可以是用户自选的合法标识符。误伤的代价是可控且诚实的：受影响的变更行只是不产生事实，若样本因此没有任何探针问题，会落入 `unprobed_samples` 并由报告标注覆盖情况——不会产生不可证伪的事实。散文词列表则刻意保持简短，因为英文单词可以是真实标识符。

**残留局限。** 一个变更行如果既无引号字符串、又无路径、且所有标识符式 token 都是散文词或保留字，就不产生任何事实。这类样本会落入 `unprobed_samples`，不进入语义分母，并在报告的 `S` 单元格标注覆盖情况（如 `0.80 ⚠ (2 of 3 probed)`），而非被静默忽略。

另一处已接受的取舍：事实按行序采集、上限 `MAX_DYNAMIC_ITEMS = 5`，因此对很长的 diff，5 条事实可能全部来自第一个 hunk。一个「保留首个 hunk、丢光其余」的压缩器仍会拿满分。这与保持分母可比的 cap 设计一致；若将来需要提高长 diff 的区分度，可改为按 hunk 或按文件分散采样。
