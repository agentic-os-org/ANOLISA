# Cosh AgentRuntime Phased Implementation and Acceptance Plan

[中文版](../zh/core-runtime-harness-implementation-plan.md)

Date: 2026-11-14. Status: recommended plan after multi-Agent evaluation; phased implementation is authorized, with phase progress and real evidence in the execution record.

Design basis: [AgentRuntime standardization and simplification design](core-runtime-harness-design.md), [Evaluation basis and decision record](core-runtime-harness-evaluation.md). Execution evidence: [Phased execution record](core-runtime-harness-execution-record.md). H0–H6 are phases of this plan and do not correspond to P0–P4 in the auto chat.

## 1. Execution Principles and Priorities

The goal is a minimal standard AgentRuntime for a Linux AI Shell, without Coding CLI feature parity. Prefer the official protocol/SDK, preserve Cosh foreground review and PTY semantics, and adopt general mechanisms from good harnesses only for actual gaps.

Freeze contracts and failure baselines first, converge the kernel and prompts in small steps, then integrate ACP and necessary enhancements. Change the default last. Auto helpers, scopes across turns, and model review pass independent candidate gates. They neither block base standardization nor enter this plan automatically because another chat develops them.

Each increment contains one main behavioral change and its regressions. Do not bundle dependency upgrades, protocol switches, prompt changes, and major refactoring. Select new parameters or behavior using actual capabilities. Never automatically probe, fall back, or retry with side-effecting requests.

### 3.2 Baselines and G0

- Pin a supported Linux image, execution identity, and build parameters; list ARM64/other-identity coverage separately. macOS does not substitute for Linux.
- Sample ordinary Shell use, short AI requests, multi-turn tools, large log output, cancellation, and 50 sessions separately, distinguishing idle and active states.

- Budget records include units, method, sample size, tolerance, failure rate, and baseline variability. P95 claims require controlled samples sufficient to estimate the tail; otherwise report observations only.
- Record existing failures, skips, uncovered cases, and environment limits individually. Do not pass by changing thresholds, skipping counterexamples, or changing samples.

G0 must state which standard functions the mainline needs, why foreground extensions are necessary, and which of the three auto routes remain experiments. Measurement and safety oracles must be reproducible. H4 cannot change the default before budgets are frozen.

For stability, improve existing max_turns, argument-error budgets, cancellation, output, and persistence before building anything else. Do not implement a workflow platform. Revalidate the final action after Hook rewrites rather than validating only initial arguments. Reuse each tool's validation instead of immediately adding a generic policy DSL.

Landed status: H1-1's S01/S02/S04 and S01b, H1-3's S05a/S05b, and H1-2's S03/S03b single-reader dispatch are implemented and verified on both macOS and Linux; see sections 10–15 of the [execution record](core-runtime-harness-execution-record.md). H1-2's asynchronous host interaction and domain-event projection, and all of H1-4, are not started; G1 has not passed as a whole.

BeforeModel declaration compaction and PreToolUse action rewriting have different contracts. The former already validates identical count/names/order and no estimated-token growth, keeping the original-declaration budget conservative; do not relax it to “fix S06.” H1c retains regression coverage for existing protections and independent prompt/profile/measurement requirements. Hook tool removal or declaration expansion is no longer a defect to fix.

### 4.2 G1

Each increment owns only applicable oracles and exits independently; the three need not merge together. H1c first selects six legacy-path task classes: explain sufficient evidence, retain uncertainty with missing evidence, never present fragments as complete, modify with authorization and verify, bounded polling succeeding after three unchanged results, and restore tools for a new task after analysis continuation. Start with one baseline/new pair per case and repeat if variable. Record total request/token/time caps; infer neither P95 nor population success rates from small samples. Use static/scripted fixtures first for the full tool/profile/purpose/approval-mode matrix. Corresponding H1a/H1b deterministic checks first cover E06/E10 partial streams, cancellation, old events, and Stop Hooks. H4 broadens real-model tasks/combinations without mixing transport, fault fixes, and prompt effects.

## 5. H2: Standard Bidirectional ACP Entries

### 5.1 Work Items and Boundaries

| ID | Scope | Deliverable and benefit | Risk and acceptance |
|---|---|---|---|
| H2-1 | Official SDK/schema adoption experiment, stdio connection, bounded I/O, correlation | Standard wire with less custom protocol maintenance | Verify existing 2.0.0 first, compare local 5.2.0 stable v1 adoption; no initial workspace-wide upgrade; Gateway/dependency/MSRV/necessary-fix checks; serial callbacks in both versions never block UI/model; frame limits before full-line allocation; bounded slow consumers/in-flight tasks |
| H2-2 | Core ACP Agent frontend | External standard clients create sessions, prompt, receive updates, and cancel | Uses the H1 kernel, no duplicated loop, advertises only actual implementation |
| H2-3 | Shell ACP Client adapter | Shell connects to Core or other ACP Agents | No Task DB/systemd dependency; handle reverse methods by actual capability; unknown mandatory requirements fail explicitly |
| H2-4 | Legacy/ACP compatibility selection | Validate coexistence of old/new versions | Select before side effects; real prompts are not capability probes; never mix wire streams |

The base scope is initialize, new session, prompt, text/tool updates, permission, cancel, and terminal state, covering mandatory Agent text/resource_link inputs and client stdio MCP configuration under the pinned v1 specification. Reuse existing MCP registry/child-process responsibilities and add a controlled stdio server fixture; built-in tools need not all become MCP. Implement resume/list/delete/config/auth as needed, advertising nothing unwired. Initially allow one active session and one in-flight prompt; reject excess explicitly and never claim unsupported multi-session recovery.

Full standard terminal/fs support is not required initially. Wire it only when a peer actually uses it and responsibilities are clear. Advertising terminal=true does not establish current-PTY delegation.

Base interoperability does not promise that an external Agent is read-only or execution-disabled. Even a scripted peer claiming analysis-only can use its own executor without requesting permission. Tests must prove Shell does not present modes, prompts, or absent terminal/fs capabilities as enforced restrictions. If a profile requires an execution ban but lacks verifiable constraints, reject it before sending a potentially execution-triggering session/prompt, rather than waiting for a tool update.

### 5.2 G2

At least one generic client uses Core base capabilities without Cosh extensions; Shell completes a standard session with a non-Cosh Agent. This proves base connectivity only. Do not change the default before foreground parity passes.

### 7.3 G4 and Rollback

G4 is an adoption-decision gate, not an unconditional default switch. After G1–G3, real interoperability, model eval, and installation validation, also compare A (direct ACP) with B (minimal internal protocol, external ACP) under the same two-process assumption. Cover at least startup, idle PSS/threads/FDs, fixed-event-stream CPU/allocations, review/cancel responsiveness, and large-output smoothness; freeze budgets first and exclude model-network variability. Never rebuild handshakes per command; retain the raw PTY hot path locally. Section 7.4 lists the itemized budgets and the no-regression checklist.

Only after A passes semantic and cost gates may a small scope switch defaults under subsequent delivery authorization. If A needs extensive private wrapping, materially exceeds budgets, or loses foreground fidelity, do not switch defaults: B continues only as a transition and a necessary fallback with unmet requirements recorded, and oracles are never relaxed for a predetermined migration. The mainline objective remains A; staying at B long term requires an explicit recorded objective adjustment, and external ACP availability cannot claim that this boundary standardization is complete. Retain explicit legacy selection; rollback stops admission, settles owners, and confirms terminal states. Dispatched actions cannot replay across protocols.

Legacy retirement requires usage and mixed-version evidence, and ordinary functions must work without Cosh extensions. Neither promise permanent dual protocols nor remove them on an unverified date.

## 9. H6: Optional Auto and Review Experiment Gates

### H6-A: Improve the Existing Deterministic Flow First

Measure confirmation reasons, false rejection, repeated questions about identical facts, and unsupported syntax. First unify final-action checks, Ask/Block, results, and owners, fixing reproducible flow problems. A missed old rule does not justify broad automatic allow, and per-tool argument rules should not grow indefinitely.

Exit: representative-task correctness does not decline, unnecessary approvals or misclassification measurably fall, and foreground semantics/hard constraints do not regress. No data means no wider automatic scope.

### H6-B: Independent Restricted-Helper Experiment

Adopt only for sufficient real demand that H6-A's deterministic flow cannot cover, independently of the protocol-topology A/B choice. Start disabled by default with one image/identity, one explicit input set, the current model, and a fixed purpose. Verify deployability under that identity, the complete boundary, normal-command correctness, startup/cleanup costs, and net approval benefit.

Do not start the target unless every necessary restriction is installed. Helper failure cannot fall back to an unrestricted Shell. stdout is not trusted proof of launch/cleanup. Verify real descendant settlement both after normal exit and after parent death.

The auto chat's C1–C7, S01–S09, and I01–I08 may supply experiment material, but the actual adopted scope must be restated. After a successful PoC, product adoption still requires rerunning applicable safety/PTY/recovery matrices against real Core/Shell and the RPM. PoC conclusions cannot substitute.

Resource scopes across turns, authorization for all data entries, purpose tracking, revocation, and summary reset remain later independent decisions; helper success does not approve them automatically. Narrow or abandon an experiment without sufficient benefit; ACP mainline completion is unaffected.

### H6-C: Additional Review Model

Evaluate only after collecting semantic cases deterministic policy cannot handle and establishing net benefit. Use independent tool-free context, minimal material, an explicitly approved model connection, and strict budgets. Timeout/invalid output grants no permission, overrides no hard ban/mandatory Ask/actual boundary, and creates no automatic long-term allow.

Compare human review, A improvements, B experiments, and the reviewer for errors, extra requests, latency, cost, and data egress. A model's “safe” judgment cannot prove a command read-only or waive isolation.

## 12. Next-Stage Scope Decision and the Final Retirement Ledger

This section is a stage-level scope convergence, not a new implementation authorization. The conclusion first: the existing Rust Core and Shell/PTY division is a sound base, the long-lived process, sessions, compaction, approval and audit already exist, and there is currently no evidence that the whole architecture must be rewritten at scale; what is needed is local governance. The main unique value of ACP is interoperability and replaceability between Shell and Agent and between Core and clients, while reductions in performance cost, code volume and maintenance cost are still unproven. The SDK queue, correlation, close and cancel problems introduced by the new ACP path are first an onboarding cost of that path, and their fixes must not all be counted as benefits of improving the old architecture. Standardization, reliability fixes and runtime net simplification are accepted separately and never merged into one kind of outcome.
